# 07 — Backend

Backend: **Firebase only**. Shared by both builds; nothing runs at home.
The phone app is in [09](09-direct-connection-and-app.md).

| Service | Use |
| --- | --- |
| Cloud Functions | one HTTPS function, `api` (Express): the callable API, playback, health |
| Authentication | email/password accounts for the people using the app; admins marked by a custom claim |
| Firestore | per-camera live state, preview, recording metadata |
| Cloud Storage | recordings |
| Hosting | `https://<project>.web.app/api/**` rewritten to the function: the address the cameras and the phone app use. Nothing else is served |

Local development: the **Firebase emulators** plus a simulated camera
(`npm install && npm run dev`). The function rebuilds on save; point the
phone app at the functions emulator. Running, testing, deploying:
[Appendix C](../appendix/appendix-c-development.md).

## How the pieces talk

```
              Firestore cameras/{key}                 Cloud Storage
         ┌──────── state, telemetry, heartbeat ◄──── recordings/{key}/*.mp4
 camera ─┤        live/preview (while watched)             ▲
  (Pi)   │                    │ read by                    │ signed PUT / GET
         └── listens for app  ▼                            │
             requests     api function ◄──── /api/call/* ──── phone app
                          (Express, one function)        (when not direct)
```

| Flow | Mechanism |
| --- | --- |
| **Camera state** | the camera writes `cameras/{CAMERA_KEY}` directly: build, state, telemetry, 5 s heartbeat ([06](06-device-software.md#firebase-link)) |
| **App command** | API call (`startTracking`, …), from a signed-in person. The function checks [whose session it is](#accounts-and-whose-recording-is-whose), validates the transition against the document and writes the new state with `stateBy: "app"`. The camera's listener applies it via `apply_state()` (same path as any command) and writes the actual result with `stateBy: "device"`; it can differ, e.g. card full |
| **State to the app** | when not direct, the phone app polls `getState` every 2 s |
| **Remote live view** | preview only: while an app calls `watch` (every 30 s), the camera writes 1 frame/s to `cameras/{key}/live/preview`. Cloud Functions can't hold a socket, so there is no stream relay. Full-rate video is direct MJPEG/WebRTC on the camera's Wi-Fi ([09](09-direct-connection-and-app.md)) |
| **Recordings** | camera → Cloud Storage on a signed URL → library ([08](08-recordings-and-cloud.md)) |

### The camera key

| Aspect | Detail |
| --- | --- |
| Value | long random string generated by `firebase-setup.sh`; `CAMERA_KEY` in the camera's `config.py` |
| Role | the camera's Firestore document id. Names the camera; on its own it lets in only the camera itself (`createUploadUrl`, `finalizeRecording`). A person's calls need them signed in too |
| Transport | `X-Camera-Key` header on every API call; `?k=` on the emulator's upload URL |
| Firestore rules | no client access at all: the phone app reads through the function, and the camera writes with its service account |
| Distribution | setup prints the key; it is built into the phone app with `--dart-define=SPORTCAM_CAMERA_KEY=…` (14 — Software setup, the app step) |
| Revocation | change `CAMERA_KEY` on the camera |

## Accounts and whose recording is whose

Several people share one camera, each with their own phone
([F15, F16](../product/01-requirements.md#functional-requirements)).

**Accounts** (`functions/src/auth.ts`). Firebase Authentication, email and
password. The app signs in over Authentication's REST API
(`src/app_flutter/lib/auth.dart`) and sends the ID token as
`Authorization: Bearer …` on every call. There is no sign-up: an admin
(custom claim `admin: true`) adds people with `createUser` from the app's
**People** page. The first admin comes from `npm run add-admin -- <email>
<password>` (`functions/src/add-admin.ts`). Forgotten passwords are reset by
email, from the sign-in page.

**Whose session, whose clips** (`functions/src/sessions.ts`, and the
camera's `owners.py`). Whoever starts a session gets its **secret**, a random
string only their phone holds. The camera (or the function, for a start
through Firebase) keeps its SHA-256, the `sessionHash`:

```
 tap Record ──► camera / API makes a secret ──► the phone keeps it (lib/keys.dart)
                  │ keeps sha256 = sessionHash
                  ├─► stop, sleep, stop tracking, record now: refused without the secret (403)
                  └─► every clip stamped with it (<clip>.owner) → finalizeRecording { claimHash }
 phone, signed in and online ──► claimRecordings { secrets } ──► claims/{hash} = { owner }
                                                                 recordings/* with that claimHash → owner
```

| Rule | How |
| --- | --- |
| Only the starter can stop it | the state carries `sessionHash`; a call leaving or advancing a session must hold a secret that hashes to it (`{secrets: […]}`, every secret the phone has). Same on the camera's own API, with no internet. Stops the camera makes itself (card full, battery, power switch, an empty room) aren't calls, and still happen |
| Everyone can see whose it is | `getState` returns `sessionHash`; the app compares it with its own secrets' hashes and greys out Stop and Sleep on someone else's. The hash can't be turned back into the secret |
| Only the owner sees a clip | `recordings/{camera}:{name}` has `claimHash` and `owner`. `getRecordings` returns the caller's clips (from every camera); playback and boxes are served to the owner alone, anyone else gets 404 |
| Ownership survives being offline | a session started on the camera's Wi-Fi has a secret only the phone and camera know. The phone registers it whenever it reaches the backend (`claimRecordings`), and a clip uploaded before or after that is then the owner's. A secret already claimed by someone else is refused |
| Through Firebase | `startTracking` makes the secret, registers it to the caller at once, writes `sessionHash` for the camera to adopt, and returns `sessionSecret` — the only time it is sent |
| A session nobody owns | `sessionHash` null: anyone may stop it, and its clips belong to no one (no one sees them)<!--with_uwb-->. With `TAG_NEEDS_PAIRING` off, an unpaired tag's<!--/--><!--both-->. With UWB, with `TAG_NEEDS_PAIRING` off, an unpaired tag's<!--/--> |

<!--with_uwb-->

**Tags.** A tag starts a session with no phone in the loop, so the camera
learns whose it is beforehand: **Pair my tag** in the app, on the camera's
Wi-Fi with only that tag switched on (`pairTag`, `pairing.py`), gives the
phone a pairing secret, and the camera keeps the tag number with its hash.
Every session that tag starts has that hash, so it is that phone's to stop
and its clips that person's. The app also starts its own sessions with its
pairing secret, so the camera follows the right tag. Pairing again replaces
the earlier pairing (a gym can lend tags out). With `TAG_NEEDS_PAIRING`
(default), an unpaired tag starts nothing.

## Tracking mode

The build is reported by **the camera**: `TRACKING_MODE` in
`src/<build>/device/sportcam/config.py`, written to its document as `mode`.
No backend setting.

<!--compare-->

| `mode` | Build | |
| --- | --- | --- |
| `with_uwb` | [with UWB](../../README.md#with-uwb) | the subject wears a tag; the tag starts and ends sessions |
| `without_uwb` | [without UWB](../../README.md#without-uwb) | vision only; the camera sweeps for a person and follows them |

- The app selects its wording from `mode` (`ModeText` in
  `src/app_flutter/lib/models.dart`).
- No `mode` (camera never connected) → treated as `with_uwb`.
- Automatic transitions (`awake` 30 s with no live viewer → `sleep`; tag off → awake, found for 3 s → recording)
  happen on the camera and arrive as ordinary state reports.
- In dev, `TRACKING_MODE` sets the simulated camera's build.

### The API

`POST /api/call/:name` with `{ data }` → `200 { result }` or
`4xx/5xx { error: { code, message } }`. The camera's own local API speaks the
same protocol ([09](09-direct-connection-and-app.md)), so the app is one
client with two possible backends.

Every call needs a signed-in person, except the camera's own two.

| Call | Does |
| --- | --- |
| `getState` | the camera's snapshot: `mode`, `state`, `sessionHash`, `telemetry`, `deviceOnline`, `whepUrl`, `upload`, `updatedAt` |
| `setPower({on})` | `sleep` ↔ `awake` (**Wake up** / **Sleep**); sleeping from any state stops a recording with it. Nothing while `off` (booting) |
| `startTracking` / `stopTracking` | `awake` or `sleep` → `tracking` (**Record** from sleep skips `awake`); `tracking`/`recording` → `awake` (stopping and saving a recording) |
| `startRecording` / `stopRecording` | `tracking` → `recording` → `tracking` |
| `watch` | an app is showing the live view: keep previews coming for a minute |
| `getPreview` | the latest preview frame, base64, with its person boxes (`size`, `boxes`) (for clients that poll) |
| `createUploadUrl` / `finalizeRecording` | the camera's, with its key alone: the recording library ([08](08-recordings-and-cloud.md)) |
| `getRecordings` / `getPlaybackUrl({camera, name})` | the caller's own library, and a playback URL for one of their clips ([08](08-recordings-and-cloud.md)) |
| `claimRecordings({secrets})` | register the phone's secrets to the caller, and hand them the clips under them: `{claimed, refused}` |
| `createUser({email, password, admin})` / `listUsers` | admins only: add a person; everyone who can sign in |

The calls that leave or advance a session (`stopTracking`,
`startRecording`, `stopRecording`, `setPower({on: false})`) take
`{secrets: […]}`; `startTracking` takes `{pairing}` (with UWB, the phone's
pairing secret) and returns `sessionSecret`.

Errors:

| Condition | Response |
| --- | --- |
| Illegal transition (e.g. `startRecording` from `awake`, or the current state) | `412 failed-precondition` (same as the camera's local API) |
| Any command while the camera is **offline** (no heartbeat for 20 s) | `412 failed-precondition`. `getState` still answers, with `deviceOnline: false` |
| Not signed in, or the token is bad or expired | `401 unauthenticated` |
| Stopping someone else's session; an admin call by someone who isn't | `403 permission-denied` |
| `createUser` for an email already used | `409 already-exists` |

## Testing

`npm test` (repo root or `src/backend`): builds the function and runs
`functions/src/api.test.ts` under `firebase emulators:exec` on dedicated
ports (runs alongside `npm run dev`). Real Express app against real Firestore
and Storage emulators.

| Area | Covered |
| --- | --- |
| State machine | happy path, illegal transitions, `setPower` idempotence, refusal while offline |
| Who stops it | the secret handed to the starter alone and registered to them; nobody else can stop, sleep or advance it; an unowned session anyone can; a paired tag's secret, and someone else's refused |
| Signing in | people's calls need a valid token; the camera's need only its key |
| Admin | only admins add or list people; duplicates and short passwords refused; an admin can make another |
| Camera key | required, well formed, names an existing camera |
| Live preview | `watch`, `getPreview` |
| Firestore rules | every client read, list and write refused, even with the key |
| Recording library | upload → finalize → the owner's list → playback with `Range`; nobody else can list, play or get a URL; a clip claimed after it uploads, and one nobody owns; boxes to the owner only; size mismatch; malformed claim hash; unsafe names; same name on two cameras |

Other sides of the contract:

- Camera: `src/<build>/device/tests/test_cloud.py`.
- Flutter app: `dart run tool/verify_against_device.dart <api> <key>`
  ([`src/app_flutter/README.md`](../../src/app_flutter/README.md#verification-without-a-flutter-sdk)).
