# 07 — Backend & companion app

Backend: **Firebase only**. Shared by both builds; nothing runs at home.

| Service | Use |
| --- | --- |
| Cloud Functions | one HTTPS function, `api` (Express): the callable API, playback, health |
| Firestore | per-camera live state, preview, recording metadata |
| Cloud Storage | recordings |
| Hosting | the Vue web app; `/api/**` rewritten to the function |

Local development: the **Firebase emulators** plus a simulated camera
(`npm install && npm run dev`). The function rebuilds on save; Vite
hot-reloads the app and proxies `/api` to the functions emulator, so the app
always calls its own origin, as on Hosting. Running, testing, deploying:
[Appendix C](../appendix/appendix-c-development.md).

## How the pieces talk

```
              Firestore cameras/{key}                 Cloud Storage
         ┌──────── state, telemetry, heartbeat ◄──── recordings/{key}/*.mp4
 camera ─┤        live/preview (while watched)             ▲
  (Pi)   │                    │ onSnapshot                 │ signed PUT / GET
         └── listens for app  ▼                            │
             requests     web app ── /api/call/* ──► api function
                          Flutter app (relay) ──────►  (Express, one function)
```

| Flow | Mechanism |
| --- | --- |
| **Camera state** | the camera writes `cameras/{CAMERA_KEY}` directly: build, state, telemetry, 5 s heartbeat ([06](06-device-software.md#firebase-link)) |
| **App command** | API call (`startTracking`, …). The function validates the transition against the document and writes the new state with `stateBy: "app"`. The camera's listener applies it via `apply_state()` (same path as any command) and writes the actual result with `stateBy: "device"`; it can differ, e.g. card full |
| **State to apps** | web app: Firestore SDK subscription. Flutter app when not direct: polls `getState` |
| **Remote live view** | preview only: while an app calls `watch` (every 30 s), the camera writes 1 frame/s to `cameras/{key}/live/preview`. Cloud Functions can't hold a socket, so there is no stream relay. Full-rate video is direct MJPEG/WebRTC on the camera's Wi-Fi ([09](09-direct-connection-and-app.md)) |
| **Recordings** | camera → Cloud Storage on a signed URL → library ([08](08-recordings-and-cloud.md)) |

### The camera key

| Aspect | Detail |
| --- | --- |
| Value | long random string generated by `firebase-setup.sh`; `CAMERA_KEY` in the camera's `config.py` |
| Role | the camera's Firestore document id, and its password |
| Transport | `X-Camera-Key` header on every API call; `?k=` on video URLs |
| Firestore rules | key holders can *read* that camera's document, preview and recordings. No *list*, no client writes; all writes go through the function or the camera's service account |
| Distribution | setup prints the app link `https://<project>.web.app/#key=…`; the web app stores the key in the browser and strips it from the address bar |
| Revocation | change `CAMERA_KEY` on the camera |

## Tracking mode

The build is reported by **the camera**: `TRACKING_MODE` in
`src/<build>/device/sportcam/config.py`, written to its document as `mode`.
No backend setting.

<!--compare-->

| `mode` | Build | |
| --- | --- | --- |
| `with_uwb` | [with UWB](../../README.md#with-uwb) | the subject wears a tag; the tag starts and ends sessions |
| `without_uwb` | [without UWB](../../README.md#without-uwb) | vision only; the camera sweeps for a person and locks on |

- Apps select their wording from `mode` (`src/web/src/lib/modeText.ts`;
  `ModeText` in `src/app_flutter/lib/models.dart`).
- No `mode` (camera never connected) → treated as `with_uwb`.
- Build-specific automatic transitions (tag off → idle, lock-on → recording)
  happen on the camera and arrive as ordinary state reports.
- In dev, `TRACKING_MODE` sets the simulated camera's build.

## Backend (`src/backend/`)

The Firebase project root:

```
src/backend/
  firebase.json          functions, hosting (→ src/web/dist), rules, emulator ports
  firebase.test.json     the same rules on other ports, for npm test
  firestore.rules        read a camera by key; no lists, no client writes
  storage.rules          deny all (recordings move on signed URLs)
  functions/src/
    index.ts             the one function: api
    app.ts               the Express app: /api/call/:name, playback, emulator upload, health
    camera.ts            the camera document, snapshots, the state machine, watch/preview
    recordings.ts        createUploadUrl, finalizeRecording, getRecordings, playback
    errors.ts            FnError → HTTP status
    api.test.ts          tests, run against the Firestore and Storage emulators
  sim/
    camera-sim.mjs       the simulated camera (Firestore + the API, like the Pi)
    frames/, sample.mp4  its test picture and its "recording"
```

### The API

`POST /api/call/:name` with `{ data }` → `200 { result }` or
`4xx/5xx { error: { code, message } }`. The camera's own local API speaks the
same protocol ([09](09-direct-connection-and-app.md)), so each app is one
client with two possible backends.

| Call | Does |
| --- | --- |
| `getState` | the camera's snapshot: `mode`, `state`, `telemetry`, `deviceOnline`, `whepUrl`, `upload`, `updatedAt` |
| `setPower({on})` | `off` ↔ `idle`; turning off from any state stops a recording with it |
| `startTracking` / `stopTracking` | `idle` → `tracking`; `tracking`/`recording` → `idle` (stopping and saving a recording) |
| `startRecording` / `stopRecording` | `tracking` → `recording` → `tracking` |
| `watch` | an app is showing the live view: keep previews coming for a minute |
| `getPreview` | the latest preview frame, base64 (for clients that poll) |
| `createUploadUrl` / `finalizeRecording` / `getRecordings` | the recording library ([08](08-recordings-and-cloud.md)) |

Errors:

| Condition | Response |
| --- | --- |
| Illegal transition (e.g. `startRecording` from `idle`, or the current state) | `412 failed-precondition` (same as the camera's local API) |
| Any command while the camera is **offline** (no heartbeat for 20 s) | `412 failed-precondition`. `getState` still answers, with `deviceOnline: false` |

## Web app (`src/web/`)

Vue 3 + Vite + TypeScript and the Firebase JS SDK (Firestore only), no UI
framework — one screen:

```
src/web/src/
  App.vue                shell; library button, upload pill, toast; key prompt if no key
  components/
    VideoView.vue        WHEP video when the camera offers it and it's reachable, else the preview
    StatusRing.vue       top-right circular indicator, colours = LED colours
    ControlBar.vue       bottom buttons, swap with state
    LibraryView.vue      recordings list + <video> player (range-seekable)
    KeyPrompt.vue        asks for the camera key if the link didn't carry it
  lib/api.ts             call(name, data) with the camera key + typed wrappers
  lib/firebase.ts        Firestore: the emulator in dev, /__/firebase/init.json deployed
  lib/cameraKey.ts       the key from the link (#key=…), kept in the browser
  lib/useCameraState.ts  live camera document, recordings and preview via onSnapshot
  lib/chime.ts           recording start/stop chimes (Web Audio)
  lib/modeText.ts        the wording that differs between with_uwb and without_uwb
```

Behaviour (requirement F5 in [01](../product/01-requirements.md#functional-requirements)):

- **Live view on open:** `VideoView` mounts immediately; no play button.
- **The status ring** (top right) and **the bottom buttons** follow the
  camera's state, with the colours, labels and buttons in
  [01 — State machine](../product/01-requirements.md#state-machine). The
  ring is hollow while the camera is offline. If acquiring stalls, a pill
  says <!--with_uwb-->"Can't see you — step into view, facing the camera"<!--/--><!--both--> (with UWB) or<!--/--><!--without_uwb--> "Can't
  find anyone — step into the room, facing the camera" (<!--/--><!--both-->without UWB, <!--/--><!--without_uwb-->after
  15 s with nobody found)<!--/-->. **Stop tracking** while recording asks to
  confirm, since it also stops the recording.
- **Chimes** (`lib/chime.ts`): rising two-note on record start, falling on
  stop (Web Audio). Armed by the first tap (browser autoplay policy). Desktop
  background tabs chime; phone browsers suspend background pages, so use the
  native app for background chimes ([09](09-direct-connection-and-app.md)).
- **No optimistic UI:** buttons `call()` a function, and the UI updates only
  when the camera's document changes. App, LED ring and other clients stay
  consistent.
- **Recording library:** ▶ button (top left, clip-count badge) opens
  `LibraryView`. Upload progress pill during upload; **"Recording saved —
  watch now"** toast when it lands. Playback: plain `<video>` on the playback
  URL (redirects to Cloud Storage; Range requests make seeking work on
  phones).

## Testing

`npm test` (repo root or `src/backend`): builds the function and runs
`functions/src/api.test.ts` under `firebase emulators:exec` on dedicated
ports (runs alongside `npm run dev`). Real Express app against real Firestore
and Storage emulators.

| Area | Covered |
| --- | --- |
| State machine | happy path, illegal transitions, `setPower` idempotence, refusal while offline |
| Camera key | required, well formed, names an existing camera |
| Live preview | `watch`, `getPreview` |
| Firestore rules | camera, preview and recordings readable by key; listing and all client writes refused |
| Recording library | upload → finalize → list → playback with `Range`; size mismatch; unsafe names; per-camera separation |

Other sides of the contract:

- Camera: `src/<build>/device/tests/test_cloud.py`.
- Flutter app: `dart run tool/verify_against_device.dart <api> <key>`
  ([`src/app_flutter/README.md`](../../src/app_flutter/README.md#verification-without-a-flutter-sdk)).
